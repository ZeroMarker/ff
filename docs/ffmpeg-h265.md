# H.265 / HEVC 源剪辑为什么慢

## 问题

对 **HEVC 源**做精准剪辑（重编码）在本机（4 核 ARM）极慢：一个 5s 段要 **~82s（0.06x）**。
H.264 源则正常。**视频本身没问题，是编码器"选错了"。**

## 根因

`rip` 旧逻辑按源编码挑编码器（初衷是"与源码保持一致"）：

| 源编码 | 旧编码器 | 结果 |
|--------|----------|------|
| H.264  | `libx264` | 快速、帧级精确 |
| H.265  | **`libx265`** | **本机极慢（5s≈82s）** |

关键事实：

- H.265 的**解码**很快（5s 段仅 **1.8s**），瓶颈几乎全在 **libx265 编码**。
- `libx265` 在本机（4 核 ARM）约比 `libx264` **慢 ~9 倍**（同一段 82.7s vs 9.2s）。
- 源 GOP（关键帧间隔）**8.33s**——`-c copy` 起点最多回退一个 GOP。

## 实测数据

来源：`MIUM-391.H265.mp4`（1920×1080，HEVC，30fps，5482s≈91min，视频 ~1.9Mbps，GOP 8.33s）。
测试段：`00:01:00→00:01:05`（150 帧，5s）。

| 测试 | 耗时 | 备注 |
|------|------|------|
| 仅解码（HEVC 帧→null） | **1.8s** | 解码不是瓶颈 |
| `libx265` 解码+编码（crf28） | **82.7s** | ← 主瓶颈 |
| `libx264` 解码+编码（crf23） | **9.2s** | 快 ~9 倍 |
| `-ss` 放 `-i` **后**（输出定位） | 33.9s | 比输入定位慢 3.7x |
| `-ss` 深 50:00 vs 浅 0:00 | 8.5s vs 2.5s | 输入快速定位有效，不会从 0 解全片 |
| `-threads 4` | ≈无改善 | 线程不是问题 |
| `-c copy`（流复制） | **0.42s** | 秒出；起点对齐关键帧 |

> 本机同时还在跑 2 个 TikTok 录流 ffmpeg（`-c copy` 割段），会抢 CPU、造成幅度波动
> （同样的 `libx264` 命令测到 9~31s 不等）。隔离测试下对比才是准确的。

## 方案与决策

剪辑**不需要保留源编码**。当前 `linux/cut.sh`（函数 `rip`）已统一用 **`libx264`（CRF 23）**：

```bash
ffmpeg -y -ss <开始> -to <结束> -i <输入> \
       -c:v libx264 -crf 23 -preset fast -c:a aac <输出>
```

- **帧级精确**：首帧 I 帧、PTS=0、时长=起止之差。
- 与 H.264 源行为一致，速度回到正常水平。
- 输出为 H.264（兼容性好）。

若仍不够快，可用 `-c copy` 秒出（不重编码、保留源码率；起点对齐最近关键帧，
本片最多回退 8.33s——只多开头一小段、终点精确）：

```bash
ffmpeg -y -ss <开始> -i <输入> -to <结束> -c copy -copyts <输出>
```
